# Door-to-Door and screen inventory (PR #182)

## Scope and sources of truth

The goal is to make Home navigation and the footer tell the same truth **without
maintaining a second random selector**. A Home refresh randomly chooses one of
the triples generated by `python/home_discovery.py`; the active Home page
then publishes precisely those three `Screen6..Screen198` destinations.

| Owner | Reused contract | Why it owns this data |
| --- | --- | --- |
| `lib/core/navigation/app_tools.dart` | `homeAppTools`, stable Door entries, `HomeDoorCatalog` | Fixed Home destinations and ephemeral selected discoveries, shared by Home and Door |
| `lib/features/home/presentation/home_screen.dart` | `pickHomeDiscoveryScreens`, `homeDiscoveryLabel` | Actually rendered Home draw; updates the snapshot after successful selection/refresh |
| `lib/shared/widgets/tool_door_selector.dart` | `HomeDoorCatalog` listener, `Navigator.of(context)` | Presentation and navigation, including `beforeNavigate` and Home stack clearing |
| `lib/core/navigation/route_names.dart`, `app_route_registry.dart` | Canonical named-route identity | Route strings are not inferred from labels or screenshots |
| `assets/home_discovery_draws.json` | Deterministic candidate triples from stdlib Python | Candidate data only, never the currently selected Home draw |

The footer contains Home + all 11 stable Home destinations + legacy Screen5
(where applicable) and up to three *actually drawn* catalogue pages. A cold
deep link, failed Home load or empty draw offers stable destinations alone.
A page previously selected but no longer featured keeps a **current-page-only**
entry, not an accidental 193-page footer.

The discovery snapshot is in-memory for this app session. It is **not** a
durable recent-pages list and should not persist stale Home selections across
restarts. Home chooses the draw; the footer only observes. This also avoids
re-randomization on every `build()`, localization rebuild or route push.

## Moving and capturing: repeatable audit

- Dart: `flutter test test/features/home/presentation/home_screen_test.dart test/shared/tool_door_selector_test.dart`
- Python candidate oracle: `python3 -m pytest python/tests/test_home_discovery.py`
- Playwright from `e2e/`: `npx playwright test tests/home_discovery_journeys.spec.ts --project=chromium`
- CI: the existing Non-Dart `Playwright E2E (auto)` lane runs the
  `@portable` journey in the configured desktop/mobile browser projects.
  Inspect its **actual job and artifacts** for the tested head; skipped jobs
  or browser emulation do not prove physical Android/iOS behavior.

The route-audit journey performs:
`Home chosen triple → Photo Studio (stable Home card) → Door menu → selected numbered screen → Home`.
It captures `home-draw.png`, `source-tool.png`, `door-menu.png`,
`discovered-screen.png`, `returned-home.png` and `route-audit.json` in `testInfo.outputPath`
(per test / per Playwright project) and attaches them to the report.
The return leg uses the measured shared Home button and confirmation dialog,
not a URL reload. Its mouse/touch records are retained in the receipt. On
failure, `flutter-semantics.json` records names, identifiers and layout boxes;
relevant Door and header observations are also printed in the job log.
The `tool-door-dropdown` semantics boundary measures the dropdown field alone.
The surrounding Card merges its title, hint and selected text; its centre and
even its merged `button` role are unsuitable for real pointer input.
Before measuring the field, the journey scrolls the actual Flutter body with
wheel input and waits for stable in-viewport geometry across browser frames.
DOM `scrollIntoView` alone can move the accessibility overlay while the canvas
remains at the top; the Chromium failure PNG demonstrated that mismatch.
The receipt records those wheel inputs as `door_scrolls`.
Mobile WebKit rejects Playwright wheel input, and its public touchscreen API
provides taps rather than native swipes. The Door helper uses real keyboard Tab
traversal to reach the field, requires observed target focus and stable full
geometry below the header, then sends a measured touchscreen tap without another
DOM scroll. Dirty Photo Studio uses the same keyboard-assisted path for Import.
Receipts distinguish keyboard reveal from touch activation; this is not native
touch-scroll coverage. A visible semantics box alone cannot authorize the tap.
Keyboard focus and geometry still do not prove canvas alignment: inspect the
pre-tap PNG and actual menu/navigation outcome. Unit mocks do not certify pixels.
Other Home/menu-item helpers retain their existing reveal behavior; this change
does not claim to solve every semantics-scroll path in the suite.
Candidate-build CI validates `CANDIDATE_SHA` against the same-job build manifest
before each journey and records `candidate_sha` plus `built_bundle_sha256` in
new receipts. Missing or mismatched candidate provenance fails the test; it is
not a skip. `ci_sha` remains GitHub's workflow SHA (which can be a synthetic PR
merge commit), not the checked-out candidate. Other local/published-site runs
leave candidate fields null rather than inventing build provenance. Existing
receipts are not rewritten. Review the manifest, exact-head checks and pixels
together; a bundle hash alone does not establish UI correctness.
URL and semantics update before Flutter's canvas route/menu transitions finish.
Captures therefore wait past the pinned SDK's 300–450ms transitions and browser
frames. `pixel_guards` stores title-region PNGs and hashes: the destination must
visually differ from Photo Studio, and the returned Home title must match the
initial Home title. A receipt cannot be complete with the old menu/dialog image.
`home-draw-header.png` is deliberately captured before Home's list is
scrolled, while the AppBar is unscrolled. `home-draw.png` still shows
the featured cards after scrolling into view. Material AppBar applies
a different `scrolledUnder` tint on that scroll: the failing mobile
Chromium/WebKit run showed background RGB (203,180,244) when scrolled,
versus (211,188,253) after returning Home. Byte-exact PNG comparison
between different AppBar states was a false failure, not a stale page.
The return-home guard now compares headers captured in the same
unscrolled state, preserving the destination's separate visual-difference
check and all real touch/mouse navigation assertions.

The receipt retains the visited routes, shared-header title, selected IDs,
project, viewport, PNG sizes and SHA-256 hashes. It asserts expected
transitions and that Home / Door content is in the viewport before capture.
The receipt is written on failure too: `stage` is `complete` only after the
return leg to Home succeeds, otherwise `failed` with `last_capture` naming the
last completed step. Each project also prints a `::notice` (stage, last capture,
IDs, route) so the result is readable from check annotations.

Locators follow Flutter's semantics: a Home card (InkWell) merges its title and
subtitle into one node, so cards are matched by title prefix and required to be
unique; Door entries are `menuitem`s matched by name. Input is the shared
browser-test-kit `press` (`e2e/utils/interaction.mjs`).
Raw screenshots can be compared manually to identify consistent and unusual UI.

This does **not** claim an automated visual-diff oracle, proof of all 198
screens, or device-native screenshot capture. Expand the sample based on
observed differences, not arbitrary full-catalog snapshot churn.

## Existing common components versus exceptions

| Surface | Current observation | Decision / question |
| --- | --- | --- |
| Page header | `shared/widgets/standard_page_header.dart` + `standard_page_shell.dart`; Home uses `custom_app_bar.dart` | Compare actual behavior, not class names; Home layout may justify a different wrapper |
| Tool footer | `StandardPageFooter` wraps `ToolDoorSelector`; some feature pages place `ToolDoorSelector` directly | The selector itself is canonical. Evaluate whether direct placement is justified by layout/dirty-state confirmation before collapsing wrappers |
| Photo Studio leave guard | `beforeNavigate` confirms unsaved changes | Preserve this gate; never centralize navigation in a way that bypasses it |
| Numbered catalogue | `GenericScreen`, specialized numbered examples, shared page shell | Route reachability and distinct widgets are already audited by `numbered_routes.toml` + route observation test; do not reimplement |
| Home actions | Previously 11 repeated inline routes and a different fixed footer list | Now backed by `homeAppTools`; add any new stable Home action in one place |
| Test UI interactions | Flutter-specific semantics and scroll timing in `e2e/utils/helpers.ts` | Keep framework adapters local until multi-repo evidence warrants extraction |
| Screenshots/evidence | `diagnostics_evidence.spec.ts`, `shared_header.spec.ts`, this route journey | Follow one evidence vocabulary; do not silently replace stronger canonical metadata receipts with screenshot presence checks |

**Observed structural exception:** `InteractivePatternExample`,
`NativeParallelPatternExample`, and `PatternSourceLinks` construct their
own `Scaffold` without a `StandardPageFooter` / `ToolDoorSelector`.
These numbered routes remain valid **targets** from Door but do not themselves
provide Door-to-Door onward navigation today. Therefore the portable audit
starts from a stable Home tool with a known footer rather than assuming any
random Screen route has one. This gap is a concrete subject for
[Issue #183](https://github.com/myon-bioinformatics/flutter_navigation_basic/issues/183);
it is not hidden by a test skip or treated as a proven crash.

## Cross-repository boundary

The portable reference is
[Browser-Test-Kit's screenshot guide](https://github.com/myon-bioinformatics/browser-test-kit/blob/main/docs/screenshot-evidence.md)
and [route-trail execution](https://github.com/myon-bioinformatics/browser-test-kit/blob/main/docs/route-trail-execution.md).
The kit supports Python and Node Playwright route walks and per-step screenshot
hooks. No new route-walk engine or vendored image verifier is needed here.
Flutter's `waitForFlutter`, semantics clicks, application scrolling and
Home-draw snapshot contract remain in this repository. If another consumer
needs the same evidence schema, agree on a portable fixture and promote only
the reusable contract, not the Flutter-specific mechanics.

## Suggested next audit slices (not unmeasured bug claims)

1. Group pages by shared header/footer and inspect real screenshots/geometry
   for layout divergence on narrow browser profiles.
2. Review direct `ToolDoorSelector` placements: determine whether they
   differ only in padding versus truly requiring lifecycle hooks/scroll layout.
3. Sample one page per numbered-pattern family plus specialized pages rather
   than capturing 198 near-duplicates by default.
4. Track visible state + page identity alongside each screenshot; a valid PNG
   and an exit code 0 alone do not prove that the intended view was captured.
5. Extract another shared widget only after two implementations have the same
   behavior contract, tests and failure handling. Record deliberate exceptions.

Do not merge evidence/artifacts generated from different PR heads or runs
into a claimed single passing matrix. Missing project or scenario evidence
must be labeled explicitly rather than counted as passed.
